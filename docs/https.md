# HTTPS and certificate setup

For standard Helm installation, follow [optional ingress and TLS](install.md#optional-ingress-and-tls): use an existing ingress controller and reference your namespace-local TLS Secret in values. Cert-manager is optional and remains separately managed; the chart does not create certificate resources.

The rest of this guide covers the optional guided installer and certificate helpers. The installer asks where to obtain an HTTPS certificate. A certificate encrypts the connection, but browsers also need to trust its issuing CA and match it to your hostname. The examples use your current kubeconfig context by default. Keep the same kubeconfig and target options from [installation](install.md); SSH execution is optional.

| Choice | Works without an existing application certificate? | Trust and renewal |
|---|---|---|
| `controller` | Yes, if the existing ingress controller provides a default TLS certificate | Browser trust and hostname coverage depend on that certificate. Controller configuration owns renewal. |
| `secret` | No; select an existing namespace-local TLS Secret | Your existing certificate workflow owns trust and renewal. The installer does not overwrite it. |
| `cert-manager` | Yes, once a ready Issuer/ClusterIssuer is configured | Requests a certificate and waits for current-generation readiness. The issuer determines trust; cert-manager renews it. |
| `private-ca` | Yes; needs OpenSSL on the installation host | Generates a private CA and hostname certificate. You manually trust the public root on your devices and explicitly renew the leaf. |

Specify a choice with `--scheme https --tls-mode MODE`, or answer the interactive questions. An explicit `--tls-secret NAME` selects existing-Secret mode unless another mode is chosen. Normal application installs never install cert-manager, a global issuer, DNS records, or device trust automatically.

## Existing/default controller certificate

Choose `controller` to use your existing ingress controller’s default TLS certificate without preparing a per-application Secret. No certificate is generated by this installer. The controller must be configured for HTTPS and may present an untrusted fallback certificate. Verify hostname coverage and browser trust before using it.

Consult your ingress controller’s documentation for its HTTPS listener and default certificate settings.

## Generate a private CA for your LAN

For a fresh private-LAN installation without existing certificate infrastructure:

```bash
./scripts/install.sh --hostname wealthfolio.example.lan \
  --scheme https --tls-mode private-ca
```

The helper generates CA and leaf keys in the protected installation state, creates only its owned TLS Secret, and verifies the certificate chain and hostname. It prints the public CA file checksum and export location. `--export-ca "$WF_CA_FILE"` selects an optional public certificate output file outside this repository; set `WF_CA_FILE` to your chosen destination. In optional SSH mode, the wrapper exports only the public root to your workstation; private keys stay on the remote host.

Verify the exported file against the printed public-CA file checksum before manually importing the root into the trust store of each device/browser you use. Certificate viewers use a different DER-based certificate fingerprint; compare that only with the separately labeled certificate fingerprint, not the PEM file checksum. No device trust store is changed automatically. Keep CA keys and application recovery keys backed up privately; never import or share a private-key file as a trust certificate.

The initial leaf lasts one year; no renewal daemon is installed. Before its printed expiry, renew explicitly:

```bash
./scripts/install.sh --configure-access \
  --scheme https --tls-mode private-ca --renew-certificate
```

Use the same target options as the original installation when renewing. Renewal retains the CA and replaces the managed leaf certificate/key, so devices keep the same public trust root. The helper refuses TLS Secrets it does not recognize as its own. Private CA rotation/expiry requires a reviewed replacement and trust update; it is not automatic.

An existing organization CA can instead be used through a ready cert-manager CA Issuer. Select `cert-manager` with that issuer and obtain its public trust root from your organization; the installer does not retrieve its CA key.

## Managed certificates with cert-manager

With a compatible cert-manager operator and ready issuer already configured, select `--tls-mode cert-manager --issuer NAME --issuer-kind Issuer` or `ClusterIssuer`. A namespaced Issuer must be in the application namespace. The installer creates a Certificate for the selected hostname and a mode-specific TLS Secret, waits for readiness, and leaves the working application route unchanged if issuance fails. It refuses conflicting Certificate or Secret resources and does not overwrite resources it does not own.

To install the operator and a public HTTP01 issuer using the current cluster:

```bash
./scripts/setup-cert-manager.sh --namespace wealthfolio \
  --issuer wealthfolio-http01 --email you@example.com --install-controller
```

The helper uses the same current-context default as the application installer; see [installation options](install.md#installation-options) for target overrides. The HTTP01 solver needs a suitable default IngressClass or an explicit `--ingress-class NAME`. Without a suitable default or explicit class, multiple controllers may serve the challenge; see [HTTP01 configuration](https://cert-manager.io/docs/configuration/acme/http01/).

`--install-controller` is a separate opt-in global operation that installs the pinned official cert-manager chart and its CRDs/RBAC. It refuses an existing operator rather than adopting or upgrading it. The locked bootstrap version is 1.21.3, supporting Kubernetes 1.33–1.36; another cluster version requires an operator installed through an appropriate upstream procedure. Without that flag the helper only creates a namespaced issuer using the existing operator.

`--dry-run` prints the HTTP01 plan without requiring a kubeconfig, client binaries or cluster access. Target resolution is deferred until execution. An explicit `--ingress-class NAME` appears in the plan; otherwise the solver leaves class selection to the cluster default.

HTTP01 requires a real domain you control, DNS pointing to the ingress, and public port 80 reachability. The helper does not configure DNS, firewalls or a domain registrar. The production ACME service has issuance limits; review the prerequisites before requesting certificates. Then select the ready issuer in the application installer, or use `--configure-access` for an existing managed installation.

For a service reachable only on a LAN, you can use a public domain you own and DNS01 validation to obtain a publicly trusted certificate. Configure your DNS provider's solver and narrowly scoped credential Secret references using the [official instructions](https://cert-manager.io/docs/configuration/acme/dns01/).

Start with the [DNS01 scaffold](../examples/cert-manager/dns01-issuer.json), fill in the provider block, and save the completed JSON outside the repository with mode `0600`. Set `WF_ISSUER_FILE` to that file and run the setup helper with `--issuer-file "$WF_ISSUER_FILE"` instead of `--email`. It accepts one JSON object containing a namespaced Issuer whose name and namespace match the selected target, and checks that scope before contacting the cluster or installing the operator. The incomplete scaffold is refused until its provider block is configured. DNS01 still requires an eligible public domain; it cannot obtain a public certificate for a private `.lan` name.

The [HTTP01 reference template](../examples/cert-manager/http01-issuer.yaml), [cert-manager installation](https://cert-manager.io/docs/installation/helm/), [issuer scopes](https://cert-manager.io/docs/usage/certificate/), and [ACME challenge requirements](https://letsencrypt.org/docs/challenge-types/) explain the underlying resources. No provider credentials are bundled or printed. Issuance and renewal depend on the operator, issuer and validation prerequisites continuing to work.
